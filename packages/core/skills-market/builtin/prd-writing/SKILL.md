# 何时使用

- 要立项一个新功能/新产品，需要对齐目标、范围与验收口径时。
- 需求方口头描述模糊，工程/设计反复追问"到底要做什么"时。
- 一个需求跨多个团队协作，需要单一事实来源(single source of truth)时。

# 执行步骤

1. 先写问题陈述：一句话说清"谁、在什么场景下、遇到什么问题、代价是什么"。方案一律往后放，问题没写清就别动笔写方案。
2. 写目标与非目标：目标用可度量的结果表述（如"注册转化率从 20% 提到 28%"），非目标显式列出本期"不做什么"，砍掉扯皮空间。
3. 描述用户与场景：列出目标用户画像与 2-3 个真实使用场景（触发-动作-预期结果），用场景倒逼需求，而非凭空罗列功能点。
4. 拆需求并定优先级：用 MoSCoW 分级——Must（不做就失败）/ Should（重要非阻塞）/ Could（锦上添花）/ Won't（本期明确不做）。每条需求挂到某个目标上，挂不上的删掉。
5. 为每条 Must/Should 写验收标准：用 "Given/When/Then" 或可勾选的判定条件，做到 QA 能照着测、无需再问。
6. 定度量指标：明确北极星指标 + 护栏指标（防止优化 A 拖垮 B），并写清埋点口径与数据来源。
7. 画范围边界：列出依赖、假设、开放问题(Open Questions)与风险，标注 owner 和待决日期。
8. 评审定稿：拉齐工程/设计/数据/业务过一轮，收敛 Open Questions 后冻结版本，变更走 changelog。

# 常见坑

- 把 PRD 写成实现说明书：规定数据库表结构、接口字段、技术选型——这是设计文档的活，PRD 只描述"要什么"和"怎么算做成了"。
- 目标不可度量："提升用户体验""优化性能"这类词等于没写，落不到验收和数据上。
- 缺非目标：不写"不做什么"，范围会在开发中无限膨胀。
- 优先级全是 Must：等于没排优先级，砍需求时无从下手。
- 验收标准缺失或含糊，导致联调/测试阶段反复返工与口径争执。
- 度量只看正向指标，不设护栏，容易为了单点数据牺牲整体。

# 检查清单

- [ ] 问题陈述在方案之前，且说清了用户、场景、代价
- [ ] 目标可度量，非目标已显式列出
- [ ] 每条需求都挂在某个目标上，并有 MoSCoW 优先级
- [ ] 每条 Must/Should 都有可测的验收标准
- [ ] 北极星指标 + 护栏指标齐全，埋点口径已定
- [ ] 依赖、假设、Open Questions 有 owner 和日期
- [ ] 通篇没有出现具体技术实现/表结构/接口字段
- [ ] 版本已冻结，后续变更走 changelog
