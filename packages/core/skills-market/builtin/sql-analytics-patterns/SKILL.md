# 何时使用

- 写分析查询、复盘报表、临时取数(ad-hoc)时。
- 查询结果对不上、跑得慢、或别人看不懂你的 SQL 时。
- 需要把一次性口径固化成可复现、可交接的查询时。

# 执行步骤

1. 先想清楚"一行代表什么":确认输出粒度(每用户?每用户每天?每订单?),后续所有 join 和聚合都围绕它。
2. 用 CTE 拆分逻辑:每个 `WITH x AS (...)` 只做一件事(过滤 / 明细 / 聚合),自上而下像流水线,别写三层嵌套子查询。
3. join 前先各自去重:对维表用 `SELECT DISTINCT key ...` 或先聚合,避免一对多 join 让主表行数翻倍。
4. 聚合时 `GROUP BY` 只放维度列,度量用 `SUM/COUNT/COUNT(DISTINCT)`;需要"每组取一条"用窗口函数而非 `GROUP BY`。
5. 需要排名 / 累计 / 环比时用窗口函数:`ROW_NUMBER() OVER(PARTITION BY user ORDER BY ts DESC)` 取每用户最新一条;`SUM(x) OVER(ORDER BY dt)` 做累计。
6. 日期分桶用 `DATE_TRUNC('day'|'week'|'month', ts)`,并显式声明时区,别依赖数据库默认。
7. 只 SELECT 用到的列;跑之前先看执行计划(`EXPLAIN`),关注是否命中分区 / 索引、是否全表扫描。
8. 查询开头写注释留痕:口径、时间窗、数据源表、作者、日期,保证他人能复现。

# 常见坑

- join 后行数暴增:多半是右表 key 不唯一,一对多导致度量被重复累加。先验证 `COUNT(*) 前后是否一致`。
- `COUNT(DISTINCT)` 与 `COUNT(*)` 混用:去重口径不明确时二者差异巨大,明确写清楚。
- `WHERE` 里对分区字段做函数(如 `DATE(ts)=...`)会导致分区裁剪失效,改用范围 `ts >= ... AND ts < ...`。
- `NULL` 参与比较和聚合:`x != 'a'` 会漏掉 `x IS NULL` 的行;`AVG` 会跳过 NULL 但 `COUNT(*)` 不会。
- `SELECT *` 在宽表 / 大表上拖慢查询且掩盖 schema 变更风险。
- 跨时区:UTC 存储、本地展示,分桶不声明时区会导致"某天"边界错位。

# 检查清单

- [ ] 已明确输出粒度(一行代表什么)
- [ ] 复杂逻辑用 CTE 拆分,无深层嵌套子查询
- [ ] join 前维表已去重,join 后行数已验证
- [ ] 去重口径(DISTINCT)明确,NULL 处理已考虑
- [ ] 日期分桶声明了时区
- [ ] 未使用 SELECT *,只取必要列
- [ ] 看过 EXPLAIN,确认命中分区/索引
- [ ] 查询头部有口径与来源注释,可复现
