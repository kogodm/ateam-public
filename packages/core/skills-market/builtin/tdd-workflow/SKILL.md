# 何时使用

需要为新功能或修复缺陷写代码、且代码路径可以被单元/集成测试覆盖时。

# 执行步骤

1. 写一个会失败的测试（RED）—— 明确"应该发生什么"。
2. 跑测试，确认它真的失败（不是因为编译错误或路径错误）。
3. 写**最小**的实现让测试通过（GREEN）—— 不优化、不重构。
4. 跑测试，确认它通过。
5. 重构（IMPROVE）—— 重命名、抽函数、消重复，保持测试绿色。
6. 检查覆盖率 ≥80%，对核心逻辑要求 ≥95%。
7. 提交（小步、可读、可回滚）。

# 常见坑

- 测试先写"现在能写的"而非"要做的事" → 写成了实现镜像，测不出问题。
- "GREEN 阶段顺手写多了" → 失去 TDD 节奏，下一步重构难。
- mock 过度 → 测的是 mock 不是代码。

# 检查清单

- [ ] 每个公开函数有至少一个 happy-path 测试
- [ ] 每个分支有至少一个测试
- [ ] 错误路径有测试（throws / 返回 error）
- [ ] 边界值（empty / null / max）有测试
- [ ] 测试隔离（不依赖运行顺序、不共享可变状态）
