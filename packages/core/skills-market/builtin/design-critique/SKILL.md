# 何时使用

- 设计稿、原型或已上线界面需要集体反馈，推进到下一阶段时。
- 团队在方案上有分歧，需要用统一标准而非嗓门大小来收敛时。
- 定期设计走查（design review），或功能上线前的可用性把关时。

# 执行步骤

1. 开场先对齐目标：主持人说明这次评审要解决什么、处于哪个阶段（早期概念 vs 临近上线），以及"今天不讨论什么"，避免跑题到无关细节。
2. 设计者先讲背景：面向的用户、要完成的任务、关键约束与已做的取舍。评审者带着"用户要达成什么"这把尺子去看，而非个人审美。
3. 反馈对事不对人：评论设计本身，不评论设计者（说"这个流程第二步用户可能找不到入口"，不说"你怎么没考虑到")。
4. 多用提问式反馈：先问"这里为什么这样设计"再下结论，常能发现你没看到的约束；把断言("这样不行")换成问题("如果用户没登录会怎样？")。
5. 明确区分两类问题：**可用性问题**（用户真的会卡住/出错，有依据）优先，**主观偏好**（我个人更喜欢另一种）要标注为偏好、不作为阻塞项。
6. 当场记录待办：每条要改的反馈落成具体 action item，注明负责人；模糊的"再打磨下"要追问到可执行。
7. 收尾对齐结论：明确哪些必须改、哪些是可选建议、哪些搁置，以及下一步和时间点。

# 常见坑

- 目标不清就开评，变成发散吐槽会，设计者收一堆矛盾意见无从下手。
- 把个人偏好当成硬伤强推，用"我觉得"压过用户数据与任务目标。
- 只否定不给方向：说"这不好"却不指出为什么、对用户有何影响。
- 评审早期概念稿时纠结像素、配色、文案等末节，浪费在还会大改的东西上。
- 反馈针对人（"你总是……"），让设计者防御、评审氛围恶化。
- 会开完没有落成待办，下次评审同样的问题再吵一遍。

# 检查清单

- [ ] 评审目标与阶段在开场已对齐
- [ ] 以用户目标/任务为准绳，而非个人审美
- [ ] 反馈对事不对人
- [ ] 尽量用提问式反馈暴露隐藏约束
- [ ] 可用性问题与主观偏好已区分并分级
- [ ] 每条反馈落成带负责人的具体待办
- [ ] 收尾明确了必改项、可选项与下一步
