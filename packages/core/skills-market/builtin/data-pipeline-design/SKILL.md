# 何时使用

- 新建 ETL / ELT 作业、定时同步、数仓分层建模时。
- 现有管道频繁失败、重跑就出错、或数据延迟 / 重复时。
- 需要评估管道成本、或排查某张表数据从哪来时。

# 执行步骤

1. 让每个作业幂等:同一分区重跑结果不变。写目标表用"先删当天分区再写入"或 `MERGE`/`INSERT OVERWRITE`,禁止纯 `INSERT` 追加。
2. 选择增量还是全量:数据量大、有可靠更新时间戳 / 自增主键时用增量;维表小、逻辑常变时用全量重建,更简单可靠。
3. 用分区组织数据:按 `dt`(日期)分区,回填 / 重跑 / 生命周期管理都以分区为单位,查询也能分区裁剪。
4. 设计 schema 演进策略:新增列用可空 + 默认值,别改列义、别删列;上游变更前有兼容期,下游解析要容忍未知字段。
5. 处理迟到数据:设定回看窗口(如重算过去 3 天分区),或用事件时间 + 水位线,避免昨天到的今天数据被漏统计。
6. 加失败重试与告警:任务加有限次重试 + 指数退避;失败、数据量骤变、SLA 超时要触发告警到人,别静默失败。
7. 记录数据血缘:声明每张表的上游依赖与产出作业,让"这个数从哪来 / 改这张表影响谁"可追溯。
8. 关注成本:控制扫描量(分区裁剪、列裁剪)、合理调度频率、清理临时表和过期分区。

# 常见坑

- 非幂等作业重跑造成重复数据或双倍计数。
- 增量依赖 `updated_at` 但上游不更新该字段,导致漏数据。
- schema 直接改列名 / 类型,下游作业静默解析错误或崩溃。
- 无迟到数据处理,跨天 / 跨时区事件被算进错误分区。
- 上游延迟时下游照常跑,产出"半截"数据还被当成功。
- 全表扫描 + 高频调度,账单飙升却没人发现。

# 检查清单

- [ ] 作业幂等,重跑同分区结果一致
- [ ] 明确增量/全量策略及其依据
- [ ] 按日期等维度分区,支持按分区回填
- [ ] schema 演进向后兼容(加可空列、不改列义)
- [ ] 有迟到数据回看窗口或水位线机制
- [ ] 有限重试 + 退避 + 失败/异常告警
- [ ] 数据血缘可追溯上下游
- [ ] 扫描量与调度频率经过成本评估
