# 何时使用

为他人或自己 review 代码前；提交 PR 前自检。

# 执行步骤

1. **意图核对**：commit message / PR 描述说的事，是不是代码真的做的事？
2. **正确性**：核心逻辑、边界、错误路径都有测试覆盖？
3. **复杂度**：函数 ≤50 行、嵌套 ≤4 层、模块 ≤800 行？
4. **命名**：变量/函数/类名表达意图，不依赖注释才能读懂？
5. **重复**：是否有可抽出的通用工具？是否重写了已存在的东西？
6. **副作用**：可变状态、全局变量、隐式 IO 是否最小化、是否文档化？
7. **错误处理**：能失败的路径都处理了？用户面信息友好，内部日志详细？
8. **安全**：参数化查询、HTML 转义、密钥不入库、外部数据全部校验？
9. **性能**：N+1、同步 IO、阻塞主循环、O(n²) 中循环？
10. **回滚**：单一职责、可独立 revert？

# 常见坑

- 只看 diff，不看上下文 → 漏掉 caller 也要改的地方。
- 抓字数（行数/格式）忽视意图 → 反而劝退作者。
- "看起来对" 没跑过测试 → review 通过、生产坏掉。

# 检查清单

- [ ] 跑过测试且全绿
- [ ] 检查了 commit message 与 diff 一致
- [ ] 至少 3 个有建设性的意见或 1 个赞同（不是橡皮章）
- [ ] 安全敏感路径用了 security-reviewer 视角
- [ ] 命名与项目惯例一致
