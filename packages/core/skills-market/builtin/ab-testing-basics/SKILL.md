# 何时使用

- 想验证某个改动(文案 / UI / 功能 / 价格)是否真的有效时。
- 团队对"哪个方案更好"有争议,需要用数据决策时。
- 上线前需要评估改动风险、避免伤害核心指标时。

# 执行步骤

1. 写明确假设:改动 X 会让指标 Y 提升 Z%,因为原因 W。有可证伪的预期才能判断成败。
2. 保持单一变量:一次只改一个因素,否则赢了也不知道是谁的功劳。多因素请用多组或因子设计。
3. 事先算样本量与实验周期:根据基线转化率、最小可检测效应(MDE)、功效(通常 80%)、显著性水平(通常 0.05)反推所需样本和天数,覆盖完整业务周期(至少一周,含周末)。
4. 随机且互斥分流:按稳定的用户标识哈希分组,保证对照 / 实验组同质、不重叠、不串组,先做 A/A 验证分流无偏。
5. 到期再看结果:实验跑满预定样本 / 周期后,看主指标的显著性与置信区间,而非只看点估计。
6. 监控护栏指标:除了主指标,盯崩溃率、延迟、退款、客诉等,防止赢了转化却伤了体验。
7. 记录与决策:留档假设、分流、数据、结论(推全 / 回滚 / 迭代),形成实验知识库供复用。

# 常见坑

- 偷看(peeking):没到期就反复看,一显著就停,极大抬高假阳性率。
- 多重比较:同时看几十个指标 / 细分,总有一个"显著",不做校正就是自欺。
- 样本量不足:功效太低,真实有效的改动也测不出来,得出"无差异"的错误结论。
- 分流有偏:两组人群本就不同(如按时段 / 渠道切),结果不可信。
- 只看相对提升不看绝对量和置信区间,小样本噪声当成效果。
- 无护栏:主指标涨了,却没发现次要指标恶化。

# 检查清单

- [ ] 有可证伪的明确假设(方向 + 幅度 + 原因)
- [ ] 单一变量,或用规范的多因子设计
- [ ] 事先算好样本量、MDE、功效与周期
- [ ] 随机互斥分流,做过 A/A 校验
- [ ] 跑满预定周期才评估,不中途偷看
- [ ] 看显著性 + 置信区间,校正多重比较
- [ ] 监控护栏指标未恶化
- [ ] 实验假设/数据/结论已留档
