# 何时使用

- 面对一个较大的功能/产品，需要从用户视角拆解并规划迭代节奏时。
- 需求是一堆零散 backlog，看不出整体用户旅程与优先级时。
- 要和团队一起切出一个能上线验证的 MVP，而不是"全做完才发"时。

# 执行步骤

1. 定用户与目标：先明确这张地图服务哪类用户、他们想达成的最终目标是什么。
2. 铺横轴（用户旅程/骨干）：从左到右按时间顺序排出用户完成目标要经历的大活动（如 浏览→下单→支付→收货），这是地图的 backbone。
3. 分解纵轴（任务与细节）：在每个活动下方，从上到下按"必要程度"排列具体任务/步骤，越靠上越核心。
4. 用 INVEST 写 story：每个 story 满足 Independent（独立）、Negotiable（可协商）、Valuable（对用户有价值）、Estimable（可估算）、Small（够小）、Testable（可测）。
5. 横切出 MVP：横向拉一条线，只保留每个活动下"走通闭环所必需"的那一行 story，形成第一个可发布的骨架版本。
6. 规划后续切片：第二条、第三条横线对应后续迭代，逐步往闭环上加厚体验。
7. 为每个 story 写验收条件：用 Given/When/Then 明确完成标准，避免"差不多做完了"。
8. 定期回顾地图：随认知更新调整卡片位置与切片，地图是活的规划工具而非一次性产物。

# 常见坑

- 把技术任务伪装成 story："搭建数据库""接入网关"没有用户价值，属于任务(task)，不该占据故事地图的格子，挂到对应 story 下即可。
- 纵轴按开发顺序排而不是按用户价值排，导致切不出真正能用的 MVP。
- MVP 切得过厚，什么都想要，退化成"迷你瀑布"，失去尽早验证的意义。
- story 太大无法估算和测试，违反 INVEST 的 Small/Testable。
- 只画一次就束之高阁，不随迭代更新，地图很快失真。
- 缺验收条件，story"做没做完"全凭感觉。

# 检查清单

- [ ] 横轴是完整的用户旅程骨干，按时间顺序排列
- [ ] 纵轴任务按用户价值/必要程度从上到下排
- [ ] 每个 story 符合 INVEST（尤其 Valuable 与 Small）
- [ ] 技术任务挂在 story 之下，没有冒充成 story
- [ ] MVP 切片走通了一条最小闭环，能真实发布验证
- [ ] 后续切片对应清晰的迭代节奏
- [ ] 每个 story 都有可测的验收条件
- [ ] 地图会随迭代与认知更新维护
