# 何时使用

接到新需求/变更后、动手写测试用例前，需要系统梳理测什么、测到什么程度、按什么顺序测时。

# 执行步骤

1. **从需求提取测试点**：逐条读需求与验收标准，把每个功能点、业务规则、状态流转、约束条件拆成可验证的测试点。显式点（"支付成功后订单变已支付"）和隐含点（并发支付、超时、金额为 0）都要列。含糊处先向 PM 澄清，别拿假设当规格。
2. **等价类划分**：把输入按"处理方式相同"分组，每组取一个代表值，避免穷举。有效等价类 + 无效等价类都要覆盖（如年龄：<0、0–17、18–150、>150）。
3. **边界值分析**：缺陷高发在边界。取边界及其两侧——最小值、最小-1、最小+1、最大值、最大±1，以及空、单元素、超长、零。数量、长度、日期区间、分页页码尤其要测。
4. **正反例并重**：正例证明功能可用；反例（非法输入、缺字段、越权、错误时序、依赖故障）证明系统能优雅拒绝并给正确错误码/提示。反例往往比正例更能暴露问题。
5. **测试金字塔分层**：大量快而稳的单元测试（分支/条件逻辑）在底、适量集成测试（API/DB/外部依赖契约）在中、少量端到端（关键用户旅程）在顶。别把能在单元层验的逻辑堆到 E2E——慢、脆、定位难。
6. **优先级排序**：按「风险 × 使用频率 × 失败影响」排。核心链路（登录、下单、支付）和高频路径先测且必须自动化；边角配置项靠后。时间有限时保高优先级全绿。
7. **界定回归范围**：依据变更影响面圈定回归集，而非每次全量。改了共享模块/公共组件时扩大范围，含其所有调用方；用依赖关系或历史缺陷聚集区指导取舍。
8. **落成验收标准**：每个测试点写清可观测的通过条件（输入→预期输出/状态/副作用），使结果非通过即失败、无需主观判断。

# 常见坑

- 只测正例（happy path），非法输入和异常时序全漏。
- 边界只测"中间的正常值"，漏掉 0/最大/空/越界。
- 把逻辑判断堆到 E2E，套件又慢又频繁 flaky。
- 需求含糊处自行脑补规格，测了个"自以为对"的行为。
- 每次都全量回归，成本高到没人跑；或反之只测改动点、漏了受影响的调用方。
- 用例写"验证功能正常"这种无法判定通过与否的模糊断言。

# 检查清单

- [ ] 每条需求/验收标准都映射到测试点
- [ ] 有效与无效等价类均覆盖
- [ ] 边界值（min/max/±1/空/超长）已列
- [ ] 正例与反例都有
- [ ] 用例按单元/集成/E2E 合理分层
- [ ] 按风险与频率排了优先级
- [ ] 回归范围依变更影响面界定，含调用方
- [ ] 每个用例有可判定的验收标准
