# 何时使用

- 做出影响面广、难以回退的技术选型（数据库、框架、通信协议、鉴权方案）时。
- 决策依赖当时的特定约束（团队规模、截止日期、既有系统），未来的人会问"当初为什么这么定"时。
- 推翻或替换一个既有决策时——要留下"为何改"的痕迹。

# 执行步骤

1. 一个决策一个文件，放进代码仓（如 `docs/adr/`），与代码一起版本管理、走同样的评审流程。
2. 文件名带递增编号 + 简短标题：`0007-use-postgres-over-mongo.md`。编号只增不复用。
3. 用固定四段模板写：**背景**（面临的问题与约束，力求客观）、**决策**（我们决定做什么，用主动句"我们将……"）、**后果**（正负面影响、带来的新约束与后续工作）、**备选方案**（考虑过的其他选项及被否原因）。
4. 标注状态：`Proposed`（评审中）→ `Accepted`（生效）→ 后续可变为 `Deprecated` 或 `Superseded by ADR-00XX`。
5. ADR 一旦 Accepted 即不可变：不要回头改内容。情况变了就写一篇新 ADR，在旧文件顶部加 `Superseded by ADR-00XX`，在新文件里写 `Supersedes ADR-00YY`，双向链接。
6. 提交前走评审：作为 PR 由相关方审阅，讨论沉淀在 PR 里，合并即代表决策生效。
7. 保持精简：一篇一两页，聚焦"为什么"而非实现细节；实现细节会过期，决策理由不会。

# 常见坑

- 事后补写：等实现完再补 ADR，就丢了真实权衡过程，沦为形式文档。应在决策当下写。
- 记"怎么做"不记"为什么"：只写结论不写理由和被否的备选，读者无法判断该决策是否还成立。
- 回头修改已生效的 ADR：破坏历史真实性。永远用新 ADR 取代旧的。
- 编号复用或不连续，交叉引用失效。
- 把 ADR 塞进 wiki/网盘，脱离代码版本，很快与实际脱节、无人维护。
- 事无巨细都写 ADR，噪声淹没真正重要的决策。

# 检查清单

- [ ] 一个决策一个带递增编号的文件，纳入代码仓
- [ ] 四段齐全：背景 / 决策 / 后果 / 备选方案
- [ ] 重点解释"为什么"，含被否选项的理由
- [ ] 状态字段清晰（Proposed/Accepted/Superseded）
- [ ] 取代关系双向链接，旧 ADR 未被就地修改
- [ ] 决策当下即写，经过相关方评审
- [ ] 篇幅精简，只记该记的重大决策
