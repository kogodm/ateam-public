# 何时使用

- 上线前想用低成本方式快速筛出界面的可用性问题，来不及做完整用户测试时。
- 接手一个现有产品，需要系统性体检交互体验时。
- 评审设计稿或竞品，需要一套公认标准给出结构化反馈时。

# 执行步骤

1. 明确范围与任务流：选定要走查的关键流程（如注册、下单），准备真实数据的可交互原型或线上环境。
2. 逐条对照 Nielsen 十大启发式走查：
   1) 系统状态可见（加载/进度/反馈是否及时）；
   2) 系统与现实匹配（用用户的语言而非黑话）；
   3) 用户可控与自由（撤销、返回、退出出口）；
   4) 一致性与标准（同一操作同一叫法、遵循平台惯例）；
   5) 防错（危险操作前置约束优于事后报错）；
   6) 识别而非回忆（把选项摆出来，别让用户凭记忆）；
   7) 灵活高效（为新手兜底，给老手快捷方式）；
   8) 美观极简（不塞无关信息稀释重点）；
   9) 帮用户识别-诊断-恢复错误（错误信息说人话、给出路）；
   10) 帮助与文档（必要时可检索、贴合任务）。
3. 独立评估再汇总：建议 3-5 名评估者各自走查后合并问题，单人漏检率高。
4. 记录每个问题：位置 + 违反的启发式条目 + 现象描述 + 截图证据。
5. 打严重度等级：0 非问题 / 1 仅表面 / 2 次要 / 3 严重 / 4 灾难级（阻断任务）。
6. 转化为改进项：按严重度×影响范围排序，产出可执行的修复建议并挂给 owner 跟进。

# 常见坑

- 只有一个人走查：单个评估者通常只能发现约 1/3 问题，务必多人独立后合并。
- 把"我不喜欢"当问题：每条问题必须绑定到具体启发式条目，否则是主观偏好而非可用性缺陷。
- 光列问题不定严重度，团队无法判断先修哪个。
- 用启发式评估替代真实用户测试：它擅长找问题，但不能证明方案对用户有效，两者互补。
- 问题描述太笼统（"体验不好"），缺位置和截图，开发无法复现和定位。
- 评估者是本产品的重度设计者，容易对既有问题脱敏。

# 检查清单

- [ ] 走查基于真实任务流和贴近真实的数据
- [ ] 十条启发式逐条覆盖，未跳条
- [ ] 有 3-5 名评估者独立评估后再合并
- [ ] 每个问题绑定了违反的具体启发式条目
- [ ] 每个问题都有位置、现象描述和截图证据
- [ ] 所有问题都打了 0-4 严重度
- [ ] 已按严重度×范围排序并转成带 owner 的改进项
- [ ] 明确了启发式评估不替代真实用户测试
