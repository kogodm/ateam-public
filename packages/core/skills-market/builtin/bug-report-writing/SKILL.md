# 何时使用

发现缺陷、需要提交一份让开发无需追问就能复现并定位的 bug 报告时。

# 执行步骤

1. **标题写清"哪里+什么条件+什么现象"**：一句话可检索、能区分同类。差："支付有问题"；好："iOS 端优惠券叠加满减时，订单金额被算成负数"。避免只写"报错""崩溃"。
2. **最小化复现步骤**：从确定的初始状态出发，用编号列出能稳定重现的最短路径，删掉与缺陷无关的操作。每步只做一件事，带上具体输入值（账号、金额、点击项）。标注复现概率（必现/偶现，如 3/10）。
3. **期望 vs 实际分开写**：明确"应该发生什么"和"实际发生了什么"，两者都要具体到可观测（金额、状态、跳转、报错文案），而非"结果不对"。
4. **环境信息**：版本号/构建号、平台与系统版本、设备/浏览器、网络、环境（test/staging/prod）、账号或数据条件、发生时间（带时区，便于查日志）。环境差异常是偶现根因。
5. **区分严重度与优先级**：严重度=对系统的技术影响（崩溃/数据错误/功能不可用/体验瑕疵），优先级=修复紧迫性（受业务、用户量、是否有绕过方案影响）。二者可背离：小众页崩溃可高严重度低优先级；文案错误可低严重度但因涉及品牌而高优先级。分别标注、别混为一谈。
6. **附证据**：日志（含 traceId/请求 ID、错误堆栈、时间戳）、截图/录屏、请求响应报文、相关数据快照。证据要能对上复现步骤的时间点。
7. **消除"无法复现"的信息缺口**：提交前自检——换环境/账号能否重现？是否漏了前置数据、特定配置、时序或并发条件？把这些隐含前提显式写出，这是偶现 bug 被打回"无法复现"的头号原因。

# 常见坑

- 标题空泛（"崩溃了"），无法检索也难去重。
- 复现步骤跳步、缺初始状态或具体输入值，开发照着走不通。
- 只写"结果不对"，不写期望值，开发不知道正确行为是什么。
- 漏版本号/环境，跨环境对不上，被判"无法复现"。
- 严重度与优先级混为一谈，排期误判。
- 截图只截结果不截关键上下文，或日志时间与操作对不上。
- 偶现 bug 不标复现概率与触发条件，直接被关掉。

# 检查清单

- [ ] 标题含位置+条件+现象，可检索
- [ ] 复现步骤最小化、编号、带具体输入
- [ ] 标注复现概率（必现/偶现 n/N）
- [ ] 期望与实际分别写清且可观测
- [ ] 版本、平台、环境、账号/数据、时间齐全
- [ ] 严重度与优先级分别标注
- [ ] 附日志（含 traceId）、截图/录屏、报文
- [ ] 已自检隐含前置条件，堵住"无法复现"缺口
